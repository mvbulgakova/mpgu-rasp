# Ревизия пайплайна, 08.09.2026

Проверка «как всё работает на самом деле» — не по коду, а по логам живых
запусков. Итог короткий: **данные не публиковались ни разу**, и это не одна
ошибка, а три, выстроенные в цепочку.

## 1. Ветка `data` не могла появиться никогда (P0, исправлено)

47 запусков `scrape.yml` подряд — все `failure`. Каждый институт падал на
шаге «Checkout data branch», лог одинаковый:

```
Initialized empty Git repository in .../data-branch/.git/
line 10: cd: data-branch: No such file or directory
##[error]Process completed with exit code 1
```

Шаг выглядел так:

```bash
if git ls-remote --exit-code --heads "$REMOTE" data; then
  git clone --branch data "$REMOTE" data-branch
else
  mkdir -p data-branch/...
  cd data-branch          # ← зашли внутрь
  git init -b data
fi
cd data-branch            # ← и ещё раз, уже изнутри неё же
```

На репозитории, где ветка `data` уже есть, работает ветвь `clone`, и
единственный `cd` проходит. На новом репозитории идёт ветвь бутстрапа —
второй `cd` падает, а `bash -e` убивает шаг. Ветка `data` не создаётся,
значит в следующий раз снова бутстрап, снова падение. Замкнутый круг.

Следствие: у PWA, Android и обоих ботов **вообще нет данных** —
`cdn.jsdelivr.net/gh/…@data` отдаёт 404.

Починено: в ветви бутстрапа больше нет `cd`, оба `git config` идут через
`git -C data-branch`. Обе ветви прогнаны на живом bare-репозитории.

## 2. Гонка бутстрапа между 17 параллельными джобами (P0, исправлено)

Даже с починенным `cd` первый успешный запуск сломался бы иначе: матрица
поднимает 17 институтов параллельно, и каждый создавал бы `data` со своим
корневым коммитом. Первый пуш выигрывает, остальные получают reject и не
могут отребейзиться поверх **несвязанной истории**.

Починено: ветку создаёт один отдельный job `bootstrap-data`, от которого
`scrape` зависит через `needs`. Бутстрап внутри `scrape` оставлен
подстраховкой. Скрипт идемпотентен — проверено повторным прогоном.

## 3. `build-teachers` клонировал `data` без проверки (исправлено)

Тот же chicken-and-egg: `git clone --branch data` без guard'а, exit 128.
Теперь при отсутствии ветки job не падает, а помечает `skip=true`, и
зависимые шаги пропускаются.

## 4. Прод крутит код из `main` — а `main` отстал (решение за владельцем)

`scrape.yml` и `bot-poll.yml` делают `actions/checkout` с `ref: main`.
Файл воркфлоу берётся из ветки по умолчанию, а **код — из `main`**.
Сейчас в `main` лежит состояние на 16.08; всё, что сделано после
(D1–D44, направление/профиль, календарь НАД/ПОД чертой, обратная связь),
живёт в `claude/schedule-app-integration-ibss01` и в прод не попадает.

Пока ветка не приедет в `main`, исправления не увидит ни один пользователь.
Это не баг кода — это решение о мерже, и принимать его владельцу.

## 5. PWA не задеплоена

`deploy-pwa.yml` срабатывает на push в `main`, GitHub Pages в репозитории
не включён (`has_pages: false`). После мержа в `main` нужно один раз
включить Pages: Settings → Pages → Source: GitHub Actions.

## 6. Мелочи, найденные попутно (исправлены)

- **Android CI падал** на тесте, который требовал невозможного: запрос
  «BOЖ09» не мог найти «БОЖ09-…», потому что латинская `B` — двойник
  кириллической `В` (Ве), а не `Б` (Бе). Ошибка была в тесте.
- **Python-бот отстал от Cloudflare-воркера**: воркер уже искал по
  направлению и профилю, бот — только по коду. Теперь паритет, и он
  закреплён тестом.
- **Тесты могли ходить в сеть.** Тест обратной связи с `request=None`
  подхватил `GITHUB_TOKEN` из окружения и создал настоящий issue в
  публичном репозитории. Теперь `scraper/tests/conftest.py` снимает
  прод-токены и подменяет `urlopen` заглушкой: выйти в сеть из теста
  технически невозможно.

## Что проверять после мержа

1. `Actions → Scrape Schedules → Run workflow` — должен появиться
   `bootstrap-data`, затем зелёные институты, затем ветка `data`.
2. `https://cdn.jsdelivr.net/gh/mvbulgakova/mpgu-rasp@data/meta/index.json`
   отдаёт JSON (CDN подхватывает новую ветку за несколько минут).
3. Бот: `/start` → код группы → под расписанием кнопка «тут ошибка».
