### Ошибка в предыдущем аудите (исправлено)

В отчёте от 26.08 утром значилось, что **arts заблокирован gdrive-ссылками**.
Это была ошибка *моего аудит-скрипта*, а не репозитория: production-код
(`scraper/main.py::gdrive_to_download_url`) корректно превращает
`drive.google.com/file/d/{ID}/view` в прямую ссылку. После использования
production-конвертации arts даёт **16 групп и 836 пар**.

### D15 подробнее — почему скан-PDF не берётся здесь

Tesseract установлен локально (`rus` + `eng`), но:

1. `_ocr_image_to_tables` детектит сетку таблицы морфологией OpenCV. На этих
   сканах линии не находятся → «Tesseract: не удалось извлечь расписание».
2. Замер сырого `image_to_string`, страница 1650×1275 @150 dpi:
   **рендер 0.2 с, OCR 226 с, 779 символов.** При ~8 страницах на файл и
   66 файлах — десятки часов.
3. Главное — **качество нечитаемое**, и это не лечится временем:

```
источник: Института международного образования на 2025-2026 учебный год
OCR:      Ивститутамеждунирулного обряжжания на 2025-2026 учебный год

источник: очная форма обучения        OCR: отния форма обучения
источник: БОЮ34-АИМ2504 (пример)      OCR: БОЮЗ-ИМ2504 / БОЮЗЕ-АИМ2ОТ
```

Коды групп искажаются до неузнаваемости. По non-negotiable проекта
«garbled group code хуже, чем missing group» — публиковать такое нельзя.

Вывод: детерминированного пути к этим файлам нет — ни здесь, ни с более
быстрым CPU.
Рабочие варианты — `scraper/hand_entry/` (ручной ввод с валидатором) либо
запросить у институтов текстовые PDF.

## Классификация нулевых файлов (после всех правок)

Скрипт `scratchpad/classify_zeros.py` разбирает КАЖДЫЙ файл, давший 0 групп,
и отделяет «парсер не умеет» от «в источнике нечего парсить»:

| Причина | Файлов | Действие |
|---|---|---|
| скан-PDF без текстового слоя (D15) | 90 | недостижимо (см. выше) |
| нет кода группы в документе (D28) | 58 | источник без кодов |
| пустой архив nextcloud | 8 | на стороне источника |
| есть «группа», но нет кода | 7 | источник |
| не сетка расписания | 3 | не расписание |
| **код есть, сетка не собралась** | **40** | **был реальный пробел парсера → D36** |

Из 40 «надо смотреть» 37 — journalism .docx, закрыты D36.

## Методика, которая себя оправдала

Ключевой приём — **сверка по физическим координатам**, а не по выводу
`extract_tables()`. Для arts именно координаты слов и раздельные списки
горизонтальных линий по колонкам доказали, что в слоте 12:40 стоят две
разные пары, а не дубликат объединённой ячейки:

```
линии колонки времени:    492 / 600 / 730 / 856
линии колонки занятий:    492 / 524 / 600 / 656 / 730 / 785 / 856
слот 12:40 (600–730) ⊃ две ячейки: КЕРАМИКА(604) + СКУЛЬПТУРА(660)
```

Без этого D19 выглядел бы как «pdfplumber продублировал merged-cell» и
был бы закрыт как не-баг — с потерей 40 % пар.

**Третий урок — параллельные пути разбора ячейки.** В кодовой базе их
оказалось ЧЕТЫРЕ: `pdf_parser._parse_timetable_cell`,
`excel_parser._parse_lesson_cell`, `excel_parser._parse_multirow_lines`,
`gsheets_parser._parse_isgo_cell`. Каждый нёс свою копию регексов на
преподавателя и аудиторию, и починка одного не чинила остальные — так
появились D31, D38, D39, D40 уже ПОСЛЕ того, как «тот же» дефект был
закрыт в первом. При следующей правке разбора ячейки надо проверять все
четыре, а лучше свести их к общему хелперу.

**Второй урок:** юнит-тест на строку может пройти, пока продовый путь
сломан. D20–D25 «зелёные» на тестах не давали никакого эффекта на
реальных файлах, потому что inline-splitter стоял под условием
`len(lines) == 1`, а после склейки блоков D19 ячейка почти всегда
многострочная. Всегда мерить на реальных файлах после каждой правки.
